# Zeek integration generation guide

Generate three files that connect an existing Spicy parser to Zeek:

1. `analyzer/<analyzer>.evt`: declares the protocol analyzers and maps Spicy units to Zeek events.
2. `analyzer/zeek_<analyzer>.spicy`: contains Zeek-specific Spicy hooks and helper functions.
3. `scripts/main.zeek`: declares Zeek events, log records, and event handlers.

The goal is compiling, useful, conservative integration. Prefer a small set of
high-confidence events and log fields over speculative deep modeling. The log is
for a network analyst, not a dump of the wire format; see "What to log".

## Architecture

Data flow usually looks like this:

```text
Spicy parser unit -> .evt on Unit -> Zeek event -> main.zeek event handler -> Log::write
```

For simple scalar fields, `.evt` can pass `self.field` directly to an event. For
complex nested units, vectors, optionals, enums, or formatting, add a `public
function` to `zeek_<analyzer>.spicy` and call that function from `.evt`.

Always keep the names consistent:

- Parser module: use the parser module exactly as provided.
- Zeek helper module: `Zeek_<Analyzer>`.
- Zeek script module: `<Analyzer>`.
- Analyzer names in `.evt`: `<Analyzer>_<Transport>`.
- Lowercase event namespace is acceptable only if the Zeek script module uses it. Prefer the provided `<Analyzer>` module consistently.

## .evt file pattern

Import the parser module and the Zeek helper module:

```spicy
import TFTP;
import Zeek_TFTP;
```

Declare the analyzers, one for each supported transport protocol. For UDP or TCP stream protocols generated by this tool,
prefer originator/responder parsing:

```spicy
protocol analyzer TFTP_UDP over UDP:
    parse originator with TFTP::Packet,
    parse responder with TFTP::Packet;
```

Map parser units to Zeek events:

```spicy
on TFTP::Request -> event TFTP::request($conn, $is_orig, self.filename, self.mode);
```

Use `if` guards when a unit contains optional alternatives:

```spicy
on BGP::Message if (self?.open) -> event BGP::open($conn, $is_orig, Zeek_BGP::create_open(self.open));
```

Use helper functions from `zeek_<analyzer>.spicy` for nested data:

```spicy
on DHCP::Message -> event DHCP::message($conn, $is_orig, Zeek_DHCP::create_msg(self));
```

## zeek_<analyzer>.spicy pattern

The helper file should define module `Zeek_<Analyzer>`, import the parser module
and `zeek`, and confirm the protocol once the entry unit parses successfully:

```spicy
module Zeek_TFTP;

import TFTP;
import zeek;

on TFTP::Packet::%done {
    zeek::confirm_protocol();
}
```

Bridge functions must be `public` when `.evt` calls them:

```spicy
public function create_request(req: TFTP::Request):
    tuple<filename: string, mode: string> {
    return (req.filename, req.mode);
}
```

Use loops over vectors to pull out the values worth logging:

```spicy
# DHCP message type from option 53, or 0 when the option is absent.
function message_type(options: vector<DHCP::Option>): uint64 {
    for (option in options) {
        if (option.code == 53 && |option.data| == 1)
            return option.data.to_uint(spicy::ByteOrder::Network);
    }

    return 0;
}
```

Use Spicy-side types in helper signatures and Zeek-compatible return types:

- `uint8`, `uint16`, `uint32`, `uint64` can return as integer values and be consumed by Zeek `count`.
- `int*` values can return as signed integer values and be consumed by Zeek `int`.
- `addr &ipv4` or `addr &ipv6` returns as `addr`.
- `bytes` can be returned as `bytes`; if Zeek script expects `string`, format with `"%s" % value`.
- Enums are safest as strings with `"%s" % value` or as counts with `cast<uint64>(value)`.
- Optional values should return as `optional<T>` or be omitted from a log record in `main.zeek`.
- Vectors should return `vector<T>` in Spicy and `vector of T` in Zeek.

## main.zeek pattern

Define the Zeek script module and exported log/event API:

```zeek
module TFTP;

export {
    redef enum Log::ID += { LOG };

    type Info: record {
        ## Timestamp of the message.
        ts: time &log;
        ## Unique ID of the connection.
        uid: string &log;
        ## The connection's 4-tuple of endpoint addresses/ports.
        id: conn_id &log;
        ## True if the message was sent by the connection originator.
        is_orig: bool &log;
        ## File requested for reading or writing.
        filename: string &optional &log;
        ## Transfer mode requested (netascii, octet, mail).
        mode: string &optional &log;
    };

    global log_tftp: event(rec: Info);
    global request: event(c: connection, is_orig: bool, filename: string, mode: string);
}

event zeek_init() &priority=5
    {
    Log::create_stream(TFTP::LOG, [$columns=Info, $ev=log_tftp, $path="tftp"]);
    }

event TFTP::request(c: connection, is_orig: bool, filename: string, mode: string)
    {
    local rec = Info($ts=network_time(), $uid=c$uid, $id=c$id, $is_orig=is_orig);
    rec$filename = filename;
    rec$mode = mode;
    Log::write(TFTP::LOG, rec);
    }
```

Use `&optional` on log fields that are not present for every event. Only assign
optional fields when you have a value.

## What to log

The log is read by a network analyst. Model it on Zeek's own protocol logs
(`dns.log`, `http.log`, `dhcp.log`): each line should say who did what, to what,
and with what result.

- Log the values that carry meaning: the operation (method, command, opcode,
  message type), its target (name, URI, path, key, identifier), parameters an
  analyst would search for (user names, host names, software versions,
  addresses), and the result (status or error code).
- Decode codes into names (`"NXDOMAIN"`, not `3`; `"BOOTREPLY"`, not `2`). If
  the parser exposes a Spicy enum, render it with `"%s" % value`. If it is a
  plain integer, map it in `main.zeek` with a `const table[count] of string`
  that has a `&default` for unknown values.
- Use typed columns: `addr` for IP addresses, `port`, `count`, `interval` for
  durations and timers, `bool`, and `vector of string` for repeated values.
- Skip wire mechanics: length fields, element counts (log the elements instead),
  checksums, padding, reserved bits, offsets and header sizes.
- For repeated elements (questions, answers, options, headers, attributes), log
  the decoded values that matter, either as their own columns or as a `vector
  of string` with one readable entry per element (e.g. `"example.com A"`).
- Do not log raw binary payloads or opaque data blocks. If the content matters,
  log its size or a short decoded summary.
- Do not stringify whole records or tuples with `fmt("%s", ...)` into a
  catch-all column; give each meaningful value its own column.
- Name columns with the protocol's terminology in snake_case and document each
  one with a `##` comment.
- Only log values the parser actually exposes. A few meaningful columns beat
  many mechanical ones.

## Worked example: simple TFTP-style analyzer

`.evt`:

```spicy
import TFTP;
import Zeek_TFTP;

protocol analyzer TFTP_UDP over UDP:
    parse originator with TFTP::Packet,
    parse responder with TFTP::Packet;

on TFTP::Request -> event TFTP::request($conn, $is_orig, self.filename, self.mode);
on TFTP::Data -> event TFTP::data($conn, $is_orig, self.num, self.data);
```

`zeek_tftp.spicy`:

```spicy
module Zeek_TFTP;

import TFTP;
import zeek;

on TFTP::Packet::%done {
    zeek::confirm_protocol();
}
```

`main.zeek`:

```zeek
module TFTP;

export {
    redef enum Log::ID += { LOG };

    type Info: record {
        ## Timestamp of the message.
        ts: time &log;
        ## Unique ID of the connection.
        uid: string &log;
        ## The connection's 4-tuple of endpoint addresses/ports.
        id: conn_id &log;
        ## True if the message was sent by the connection originator.
        is_orig: bool &log;
        ## Kind of message (REQUEST, DATA).
        message_type: string &log;
        ## File requested for reading or writing.
        filename: string &optional &log;
        ## Transfer mode requested (netascii, octet, mail).
        mode: string &optional &log;
        ## Block number of a DATA message.
        block: count &optional &log;
        ## Number of file bytes carried by a DATA message.
        size: count &optional &log;
    };

    global log_tftp: event(rec: Info);
    global request: event(c: connection, is_orig: bool, filename: string, mode: string);
    global data: event(c: connection, is_orig: bool, block: count, payload: string);
}

event zeek_init() &priority=5
    {
    Log::create_stream(TFTP::LOG, [$columns=Info, $ev=log_tftp, $path="tftp"]);
    }

event TFTP::request(c: connection, is_orig: bool, filename: string, mode: string)
    {
    local rec = Info($ts=network_time(), $uid=c$uid, $id=c$id,
                     $is_orig=is_orig, $message_type="REQUEST");
    rec$filename = filename;
    rec$mode = mode;
    Log::write(TFTP::LOG, rec);
    }

event TFTP::data(c: connection, is_orig: bool, block: count, payload: string)
    {
    local rec = Info($ts=network_time(), $uid=c$uid, $id=c$id,
                     $is_orig=is_orig, $message_type="DATA");
    rec$block = block;
    rec$size = |payload|;
    Log::write(TFTP::LOG, rec);
    }
```

## Worked example: complex DHCP-style bridge

When the parser has nested units or vectors, use a bridge function:

`.evt`:

```spicy
import DHCP;
import Zeek_DHCP;

protocol analyzer DHCP_UDP over UDP:
    parse originator with DHCP::Message,
    parse responder with DHCP::Message;

on DHCP::Message -> event DHCP::message($conn, $is_orig, Zeek_DHCP::create_msg(self));
```

`zeek_dhcp.spicy`:

```spicy
module Zeek_DHCP;

import DHCP;
import spicy;
import zeek;

on DHCP::Message::%done {
    zeek::confirm_protocol();
}

# DHCP message type from option 53, or 0 when the option is absent.
function message_type(options: vector<DHCP::Option>): uint64 {
    for (option in options) {
        if (option.code == 53 && |option.data| == 1)
            return option.data.to_uint(spicy::ByteOrder::Network);
    }

    return 0;
}

# Host name from option 12, or empty when the option is absent.
function host_name(options: vector<DHCP::Option>): bytes {
    for (option in options) {
        if (option.code == 12)
            return option.data;
    }

    return b"";
}

public function create_msg(msg: DHCP::Message):
    tuple<
        op: uint64,
        xid: uint32,
        client_ip: addr,
        your_ip: addr,
        msg_type: uint64,
        host_name: bytes> {
    return (
        cast<uint64>(msg.op),
        msg.xid,
        msg.client_ip,
        msg.your_ip,
        message_type(msg.options),
        host_name(msg.options)
    );
}
```

`main.zeek`:

```zeek
module DHCP;

export {
    redef enum Log::ID += { LOG };

    type MessageLog: record {
        op: count;
        xid: count;
        client_ip: addr;
        your_ip: addr;
        msg_type: count;
        host_name: string;
    };

    type Info: record {
        ## Timestamp of the message.
        ts: time &log;
        ## Unique ID of the connection.
        uid: string &log;
        ## The connection's 4-tuple of endpoint addresses/ports.
        id: conn_id &log;
        ## True if the message was sent by the connection originator.
        is_orig: bool &log;
        ## BOOTP operation (BOOTREQUEST or BOOTREPLY).
        op: string &log;
        ## Transaction ID linking a client request to the server's reply.
        trans_id: count &log;
        ## DHCP message type (DISCOVER, OFFER, REQUEST, ACK, ...).
        msg_type: string &optional &log;
        ## Address the client already holds.
        client_addr: addr &log;
        ## Address offered or assigned by the server.
        assigned_addr: addr &log;
        ## Host name sent by the client.
        host_name: string &optional &log;
    };

    global log_dhcp: event(rec: Info);
    global message: event(c: connection, is_orig: bool, msg: MessageLog);
}

const op_names: table[count] of string = {
    [1] = "BOOTREQUEST",
    [2] = "BOOTREPLY",
} &default=function(n: count): string { return fmt("unknown-%d", n); };

const msg_type_names: table[count] of string = {
    [1] = "DISCOVER",
    [2] = "OFFER",
    [3] = "REQUEST",
    [4] = "DECLINE",
    [5] = "ACK",
    [6] = "NAK",
    [7] = "RELEASE",
    [8] = "INFORM",
} &default=function(n: count): string { return fmt("unknown-%d", n); };

event zeek_init() &priority=5
    {
    Log::create_stream(DHCP::LOG, [$columns=Info, $ev=log_dhcp, $path="dhcp"]);
    }

event DHCP::message(c: connection, is_orig: bool, msg: MessageLog)
    {
    local rec = Info($ts=network_time(), $uid=c$uid, $id=c$id,
                     $is_orig=is_orig, $op=op_names[msg$op],
                     $trans_id=msg$xid, $client_addr=msg$client_ip,
                     $assigned_addr=msg$your_ip);

    if ( msg$msg_type != 0 )
        rec$msg_type = msg_type_names[msg$msg_type];

    if ( |msg$host_name| > 0 )
        rec$host_name = msg$host_name;

    Log::write(DHCP::LOG, rec);
    }
```

## Common pitfalls

- Do not invent parser module or unit names. Use only names found in the supplied parser.
- Do not call a helper from `.evt` unless it is declared `public`.
- Do not forget `import Zeek_<Analyzer>;` in `.evt` when using bridge functions.
- Do not use Zeek `record` syntax inside `.spicy`; use Spicy `tuple<...>`.
- Do not use Spicy `vector<string>` syntax in Zeek scripts; use Zeek `vector of string`.
- Keep event names declared in `main.zeek` exactly aligned with `.evt`.
- Do not copy the parser's fields one-to-one into the log; follow "What to log".
- Include a `%done` confirmation hook for the entry unit.
- Do not add `%error` hooks calling `zeek::reject_protocol`.
